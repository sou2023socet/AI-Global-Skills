# Implementation Roadmap

**Status:** Proposed sequence; each phase requires review before implementation. This roadmap does not authorize migration of source skills.

## Dependency order

```text
Owner review
  -> registry/skill contract
  -> discovery and project-context evidence
  -> candidate/resource provenance and lifecycle catalogue
  -> selection, dependency/conflict/permission policy
  -> workflow composition
  -> static validation and safe scenarios
  -> reviewed pilot migration
  -> domain-by-domain expansion
  -> optional integrations/reports/automation
```

## Phases and gates

| Phase | Scope and deliverables | Reuse or enhancement | Dependencies and risks | Acceptance and verification tests | Rollback/preservation |
|---|---|---|---|---|---|
| 0. Proposal review | Approve directory map, ownership, candidate dispositions, and source boundaries. | Prior inventory/mapping and source orchestrator references. | Unreviewed proposal may encode wrong canonical ownership. | Owner accepts/amends architecture and identifies a pilot; no implementation claim. | Proposal docs can be revised without touching source libraries. |
| 1. Registry and skill contract | Finalize JSON Schema, status lifecycle, provenance model, contract version policy, and authoring template. | Global authoring guide/validator and enterprise metadata schema/skill governance. | Schema mismatch with host platforms; status may overstate evidence. | Positive/negative fixture cases; reject invalid metadata, bad IDs, missing provenance, invalid statuses; documented compatibility mapping. | Version schema; do not transform source entries yet; retain prior proposal. |
| 2. Discovery and project-context foundation | Define non-secret project registry, context/evidence format, freshness, source paths and project-isolation template. | Both discovery skills, project assessment schema, report templates. | Secrets/data leakage, stale project identity, unclear repository ownership. | Fixtures prove ambiguous IDs stop, sensitive values redacted, stale evidence marked, project records isolated. | Templates can be reverted; never copy project code or credentials. |
| 3. Catalogue and candidate traceability | Create reviewed source records for selected pilot only; classify all candidate IDs and their resource form without making all skills. | Existing 80-candidate catalogue, traceability/dependency matrices, source registry. | Treating candidate coverage or inventory as implementation evidence; licensing/provenance unknown. | All IDs 01–80 resolve to a disposition; source path/hash exists for approved pilot entries; missing IDs fail validation. | Remove only newly introduced catalogue entries; source files remain unchanged. |
| 4. Selection and orchestration policy | Specify trigger matching, minimal skill set, required/optional dependencies, conflict resolution, permission categories, ordering and checkpoints. | Enterprise master orchestrator, routing/dependency policies, build/test approval boundary. | Over-selection, dependency cycles, conflicting file ownership, approval bypass. | Deterministic fixtures for matching/non-matching triggers, topological order, cycles, conflicts, approval denials, and failure resume. | Disable policy release and return to reviewed static selection; no executor to shut down. |
| 5. Static validator and reports | Build schema/reference/dependency/candidate/overlap validator and generated catalogue/coverage reports. | Existing validator/check scripts as reviewed source, not copied blindly. | False-positive/negative similarity, broken links, generated reports mistaken for proof. | Valid/invalid corpus; all links and provenance checked; duplicate output requires human review; reproducible report diff. | Preserve source inputs; remove generated output only if generated by this project and confirmed safe. |
| 6. Workflow scenario suite and pilot | Add safe deterministic scenarios for discovery, requirements, testing gate, and handover. Prepare one approved pilot migration proposal. | Existing discovery, SDLC, test, approval, and workflow skills. | Scenario fixtures may not represent target hosts; shared source files are already dirty. | Trigger/non-trigger, required outputs, approval gates, safe failure/recovery, and evidence provenance pass in isolated fixture projects. | Pilot isolated to new project; abandon new copies and keep source untouched. |
| 7. Selective domain migration | Migrate only explicitly approved skills/templates, one domain at a time; update compatibility map and deprecations. | Select from 143 inventoried source skill files; focus on reuse and adaptations, not counts. | Large duplicate surface and unknown source status; careless merge can lose platform-specific behavior. | Source/destination hashes, owner, change diff, compatibility scenarios, consumer map, and rollback recorded per resource. | Restore from the new-project migration snapshot; never alter source roots. |
| 8. Platform adapters | Add host-specific discovery/config only after portable core is stable. | Existing `.github/skills` structure and agent-platform guidance. | Divergent metadata/trigger behavior and tool permissions. | Platform-specific discovery and invocation tests; adapter cannot weaken global permission rules. | Disable adapter independently; canonical skill contracts remain intact. |
| 9. Optional integrations and reporting | Consider MCP/automation, audit storage, generated dashboards, and scheduled checks. | Existing MCP skill, workflow scheduling, logging/monitoring guidance. | Credential exposure, retention/privacy, unexpected execution/cost, false health signals. | Threat/privacy review, opt-in and least privilege, bounded side effects, freshness and access tests. | Feature flags/adapter removal; retain source reports; no irreversible storage migration. |

## Initial priority

Prioritize Phases 1–5 before any runtime or advanced automation. Specifically: schema and contract first; project identity/context next; then evidence/registry and candidate traceability; orchestration policy; validation and generated reports. Keep dashboard, persistent event storage, task queue, parallel agents, knowledge ingestion, and autonomous scheduling deferred.

## Exit criteria for the foundation

- Registry schema has an agreed version and representative valid/invalid fixtures.
- Every candidate 01–80 has an explicit resource-form decision and source coverage link.
- No skill is promoted to a stronger status without the matching validation evidence.
- Project-specific code/data stays outside global skill packages.
- Dependency cycles, invalid references, duplicate IDs, and missing candidate mappings are detected.
- Approval, conflict, and failure-recovery scenarios fail closed.
- A pilot migration has a named owner, reviewed source, hash/provenance record, acceptance checks, and rollback.
